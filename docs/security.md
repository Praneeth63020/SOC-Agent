# Security notes (final, Day 5)

What the agent can and cannot do, where each control is enforced, and the test that proves it. All data is **SYNTHETIC**. IP intelligence and CVE data come from a **MOCK** feed (`live: false`). **Nothing real is ever blocked, disabled or isolated**: an approved action is only *simulated*, and only after an analyst decides.

## Trust boundaries

```
  model (NVIDIA NIM or the MOCK script)
     │  can only emit tool calls
     ▼
  Hermes agent  ── enabled_toolsets=["soc"], narrowed to the tools of the current phase
     │            unknown tools -> refused_by_hermes (never dispatched)
     ▼
  tool wrapper (tools/base.py) ── schema in/out, permission, timeout, exception capture, audit
     │   read tools        get_alert, search_logs, lookup_ip, search_cve, get_asset_context, correlate_evidence
     │   write_internal    submit_* (validated), request_action (creates a PENDING request only)
     │   disruptive        block_ip / disable_account / isolate_host: never registered, always denied
     ▼
  SQLite history + audit trail (store.py)   append-only, hash-chained
     ▲
     │  separate path, no tool wrapper, never imported by the tool layer
  analyst CLI / API (approvals.py)  approve | reject | execute (SIMULATED) | close
     X-Analyst-Token on the API (secrets.compare_digest)
```

## Residual risks

- **Write access to the database file defeats tamper evidence.** The chains detect a modified, deleted or reordered row and a row inserted without a hash. Someone with write access to `state/soc.db` who knows the scheme can still drop the triggers and recompute every hash, *append* correctly hashed forged rows (e.g. an approved decision), or cut rows off the end of a chain: the chain heads are not anchored outside the database. Production would ship each chain head to a write-once store (WORM bucket, SIEM) or sign it, and keep the database on a host the agent process cannot write to directly.
- **Evidence rows are append-only, not chained** (Day 5 review). A forged evidence row inserted outside the application could make `request_action` accept a target nothing returned, or show a fabricated excerpt in the report appendix. It needs file write access (as above), and every request still waits for an analyst.
- **Rows from before Day 5.** Databases created earlier have unchained `phases` / `reports` rows; they are accepted as a prefix of each table (`verify-audit` shows how many), so tampering with those old rows is not detectable. Expiries before Day 5 have no `action_events` row: `verify-audit` reports such an action as inconsistent (move an old database aside; `state/` is git-ignored).
- **One shared analyst token.** The API token proves "an analyst", not which one; the `analyst` name in the body is self-declared. Production needs per-user authentication (SSO/OIDC) and role checks, with the name taken from the identity, not from the body.
- **Read endpoints are open.** `GET /investigations…`, `/actions` and `/report` need no token. They change no decision, but they show task prompts, tool results and evidence excerpts, and they refresh the report version and mark overdue actions as expired. `serve` binds to 127.0.0.1 by default; anything wider needs authentication in front.
- **Unauthenticated intake.** `POST /alerts/run` (like the Day 1-3 intake endpoints) needs no token: whoever can reach the API can start runs (NVIDIA cost), and the entities of an alert they submit are valid `request_action` targets. Requests still wait for an analyst. Production would authenticate the SIEM-to-API intake.
- **Pending requests are written at once, tool calls at phase end.** A `request_action` row is committed when the tool accepts it; its tool-call audit row is written when the phase ends (in the same process, before the JSON export). A hard process kill in between leaves a pending action whose request row (agent, reason, refs, time) is the only record of it.
- **Same-host trust.** The CLI analyst commands trust whoever can run them on this machine. The separation is between the *agent* and the analyst path, not between local users.
- **Attacker-controlled entity values.** Text inside a log message never becomes a target, but some entity *fields* come from attacker input: an `Invalid user admin from …` line puts `admin` in the account field. If such an event is in this investigation's evidence, a fooled model's `request_action disable_account admin` passes the target check and is recorded as **pending**. It still cannot run without an analyst's approval, and the reason and refs are shown with it. (In the shipped compromise data the `admin` attempt is on another host and outside the searches, and the injected line L68 has no entity fields.)
- **Prompt injection beyond actions.** A model fooled by log text can still write misleading prose: the executive summary, recommendation text, or a wrong severity in the findings. That prose is checked for refs, MOCK labels and containment wording, but not for meaning. The rubric comparison and the evidence appendix let the analyst check it; they don't prevent it.
- **Fuzzy tool-name repair in Hermes.** Hermes may rename a near-miss tool call (`execute_action` → `request_action`, `reject_action` → `request_action`). It can only land on a tool the phase exposes, and every such call is fully validated, but the audit row shows the repaired name; Hermes logs the original.
- **Calls Hermes refuses are not timed by Hermes.** Their audit rows carry the previous call's timestamp and no duration. When Hermes stops a run after three consecutive invalid calls, the last one is recorded from Hermes's error message.
- **Excerpts and caps.** Tool results above 20,000 characters are stored as a preview (`result_truncated`); the evidence index keeps a 240-character excerpt per ref.
- **Hermes request dumps.** On an API error Hermes writes a request dump to `.hermes/sessions/` (the prompts and tool results of that call: SYNTHETIC data only; the API key is masked as `nvapi-xx...xxxx`). `.hermes/` is git-ignored and excluded from the submission zip (`git archive`).
- **Analyst-name heuristics.** The check refuses names that are, start with or end with a word of the agent / automation (`hermes`, `agent`, `system`, ...). That can refuse a real name such as "Systema Rao" (use another form of the name); it is a guard against the agent's own name, not authentication.
- **Failed runs stay "Under Investigation".** A run whose plan or assessment failed keeps that status until an analyst closes it; `history` shows the phase status in the audit (`audit INV-...`).
- **Simulation only.** No connector to a firewall, directory or EDR exists. If one were added, it would need its own credentials, a dry-run mode, and a second-person rule for high-impact targets.

## Day 5 review: findings and what was done

An independent review of the whole code base against the brief's constraints (no fabricated evidence, labels, no real systems, data minimization, auditability, approval gate) found these issues. High-priority ones were fixed with a regression test; the others are documented above.

| # | Finding | Priority | Outcome |
|---|---|---|---|
| 1 | `execute` trusted the mutable `pending_actions.status`: a rejected action whose status was edited to `approved` in the database could be executed, and `verify-audit` still said OK | high | **fixed**: `execute` needs an approved decision row; `verify-audit` checks action states (threat 5, 10) |
| 2 | `phases` and `reports` were not chained: an assessment row inserted with plain SQL changed the report's severity unnoticed | high | **fixed** for phases and reports (threat 10); evidence rows and correctly hashed appends: residual risk |
| 3 | Only the last of several expiries was recorded in the audit trail | high | **fixed**: one chained `action_events` row per expiry |
| 4 | Fault injection was not labelled in `run` output or the incident report | high | **fixed** (threat 13) |
| 5 | The report's SYNTHETIC label followed the alert's flag, not the data | high | **fixed** (threat 14) |
| 6 | Agent / log text could inject Markdown links and images into the report | high | **fixed** (threat 7) |
| 7 | A pending action is committed before its tool-call audit row (written at phase end) | medium | residual risk ("Pending requests are written at once") |
| 8 | Agent names with digits or prefixes (`Hermes2`, `AgentSmith`) passed the analyst-name check | low | **fixed** (threat 5) |
| 9 | `actions execute --analyst` help text said it defaults to the approver | low | **fixed** (the record says "not named; approved by X") |
| 10 | Failed runs keep the status "Under Investigation" | low | residual risk |
